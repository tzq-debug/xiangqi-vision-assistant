# 调试记录

这份文档记录开发过程中踩过的坑，按主题组织（不按时间流水），每条固定写成
**现象 → 根因 → 修法 → 教训**。

写在最前面的一句话：这个项目 90% 的 bug **不是「识别算法不够好」，而是「盘面在
不知不觉中错了，程序还在自信地给建议」**。真正难的不是认出一个棋子，而是知道
自己什么时候认错了——以及错了之后宁可闭嘴。

---

## 一、识别：盘面读错

### 1. 上一步落点的小光点被当成棋子（最顽固，前后栽了三次）

**现象**
- 第一次：`(0,4)` 空位被判成黑「士」，凭空多一个士，FEN 直接非法，算棋被静默跳过；
- 第二次：同一格在相邻帧之间一会儿读成「将」、一会儿读成「马」，盘面出现 2 个将 / 3 个马；
- 第三次：光点正好压在上一步棋子的**原位置**上，导致「帅离开原位」这一半根本没被检出。

**根因**
JJ象棋 会在上一步落点显示一个白色十字光点。它亮度极高（接近纯白），
占空判定（按格中心亮度）认为「这格有子」，模板匹配又只能硬凑一个字给它。

**修法（三层）**
1. `board.sanitize_positions()`：按帅/士/象的**合法落点**清掉越界棋子
   （士只走九宫对角、象不过河、帅不出九宫），位置非法的必是幻觉；
2. `recognize._enforce_counts()`：某类棋子超数量上限时，按置信度清掉多余的；
3. `recognize.GHOST_MAX_SCORE = 0.50`：占空图说有子、但模板最高分低于 0.50 时判**空**。
   实测真棋子最低 0.55（将帅），光点只有 0.42。

**教训**
「有子/无子」不能只靠亮度。光点比棋子还亮，任何单阈值判据都会被它骗过去；
必须叠加「形状（外圈是否也亮）」和「像不像某颗子（模板分）」两道判据。

---

### 2. 红方棋子被认成黑方棋子

**现象**
黑方局里，红马读成 `n`（黑马，0.82 比红马 `N` 的 0.74 还高）、红车读成 `r`。
紧接着数量纠错把这些「多余的黑子」删掉，一整条底线丢了三个子。

**根因**
模板是**带背景的方块**（裁剪一格 140×140 缩放到 80×80）。棋盘最上/最下两行外侧是
亮的山水画背景（y=260 处亮度 177，棋盘区域只有 81），红子那格混进了更多亮背景，
与「白底黑字」的黑子模板反而更像。

**修法**
`recognize._fix_color()`：取格中心圆内**最暗 15% 像素**的 R-G 均值，用它纠正大小写。

| 内容 | R-G 均值 |
|---|---|
| 红方棋子 | **+138** |
| 黑方棋子 | **≈ 0** |
| 空位 | -22 |

阈值 60，只看棋子墨色、与背景无关，非常稳。

---

### 3. 车和马分不清，导致「凭空少一个车」

**现象**
用户一眼看出盘面少了一辆车。清点发现是 `R:1 / N:3` —— 两个红车都被认成了红马。

**根因**
同一格上 `N(马) 0.91` 与 `R(车) 0.90`，**只差 0.01**。模板在这个分辨率下车/马字形
区分度极低。而 `_enforce_counts` 遇到「马超上限」时，把多出来的那颗**直接删掉**，
于是车就这么没了。

试过但无效的路子：
- 用高清开局图（1256×2760）重提模板 → 结果与旧模板识别完全一致；
- 改用 Canny 边缘图做匹配 → 分数掉到 0.08~0.16，区分度更差。

**修法**
超量时**先改判、再删除**：看该格次高分能不能落到「同方还没到数量上限」的棋子
（要求 ≥ `REBALANCE_MIN_SCORE = 0.70`，真棋子错认时次选通常 0.8+，而光点那种假棋子
次选很低，仍会被清掉）。同一张截图从 `R:1/N:3` 修正为 `R:2/N:2`。

**教训**
字形相近的棋（车/马/炮）不要指望模板区分，**用「数量上限」这条硬约束兜底**。
超量本身就证明识别错了，此时次高分往往就是正确答案。

### 4. 网格精修把整张网格推走一格

**现象**
黑方局启动后整盘错行：两条底线全空、中间行串位，识别出 13 个棋子（应 32 个）。

**根因**
`fit_grid` 的圆盘拟合偶尔会锁到相邻一行，把四角推走 **1.02 格**。

**修法**
`calibrate.refine_rectify(..., max_shift_frac=0.7)`：修正幅度超过 0.7 格就判失败，
退回配置里的四角（人工标定的可靠值）。

**教训**
精修的定位是「把标定时落在外框上的四角拉回交叉点网格」，正常工作量约**半格**。
给了无上限的自由度，它就会跑偏；上限设 0.45 又太严——测试里「四角外扩 70px（0.5 格）」
这种正当场景会被误拒（踩过一次）。

---

### 5. 残局时精修必然失败，然后永久用偏掉的四角

**现象**
残局（十几个子）启动，日志告警「网格自动精修失败」，之后整场识别都错位，
用户看到的是「同一辆车一会儿认成马、一会儿认成炮」。

**根因**
精修靠检测实心圆盘拟合网格，**棋子太少就没法拟合**。而原逻辑「只试一次，失败就用
标定四角继续」——标定四角与真实网格差几像素，顶部可忽略，到最后一格积成了一整格。

诊断证据：关键格匹配分只有 **0.19~0.26**（正常真棋子 0.55~0.89），说明采样窗口根本
没套在棋子上；而旁边的空格反倒拿到 0.76（滑动窗口把邻格的车抢了过来）。

**修法**
失败后**每 15 帧（约 30 秒）重试**，一旦棋子变多（开新局）拟合成功，就用新四角
**重建整盘**（`tracker = None`）。这样残局启动也能在下一局自动纠正回来。

**教训**
「只试一次然后放弃」在这种随局面变化的环境里是错的。同样的道理也适用于
「子力校验」「可信度守门」——都要留自动恢复的路径。

---

### 6. 「只多不少」被当成噪声吸收，走子彻底丢失

**现象**
红帅横移一步，程序毫无反应。日志里只有 `srcs=[] arrived=[(9,4)]`，然后
「纯噪声已吸收为新基准」。

**根因**
真实走子必然「一少一多」。但落点光点压在原位置上时，「离开」那一半看不出来，
只剩「新位置多了个棋子」。原逻辑认为这「不可能是走子」，把它吸收成新基准帧——
于是**基准帧和盘面永久错开**，这颗子以后再动也检不出来。

**修法**
不再吸收，累积到 `RESYNC_POLLS`（6 帧）就请求整体重同步，用重新识别把盘面拉回来。

---

### 7. 滑动窗口太宽，空位被邻格的棋子「蹭」出高分

**现象**
空位偶尔被判成有子，且凭空造出来的那个子位置看着完全合法。

**根因**
模板匹配留了 `0.11 * cell` 的搜索余量（为了抗网格抖动），窗口实际宽过一格，
邻格的棋子能滑进窗口中心拿到高分。

**修法**
不缩窗口（缩了抗抖动能力就没了，实测 pad 从 0.11 降到 0.07/0.04，识别出的棋子
从 25 掉到 22/18），而是靠 `GHOST_MAX_SCORE` + 数量上限把这些「合法但错」的格子兜掉。

## 二、追踪：走子丢了

### 8. 重同步采纳盘面后，回合没跟着切换

**现象**
红方走完一步，盘面更新了，但程序一直「等对方走」——一步建议都不给。

**根因**
那步被识别成「多格变化」，走的是重同步的**整体采纳**分支。分支里只重建了盘面，
`side_to_move` 还停在上一步的走子方。

**修法**
重同步前后盘面有变化，就把回合切给对方（新局重建除外，那条路径自己会设红先）。
原则：**宁可多给一条建议，也别彻底哑掉**。

---

### 9. 打完一局再开一局就「哑火」（修了三轮）

**第一轮现象**：新局一步建议都没有。
**根因**：新局比刚结束的残局多出十几个子，子力校验（一步最多吃一个）把它当成
「凭空多子」，一直拒绝采纳，程序永远卡在旧残局基准上。

**第二轮**：加了新局快速通道，但判据写的是「旧盘 ≤20 子」，而实测那局结束时**还剩 26 子**，
于是没被识别，白等三轮重试（2 分 40 秒后才靠强制校准恢复）。

**第三轮**：判据改成更本质的——**正常对局子力只会减少（吃子），任何「变多」都只能是
盘面重置**。判定条件：`新盘 ≥ 28 子 且 新盘 > 旧盘`。

**第四轮**：盘面重建成功了，但还是不出建议——因为**只重建了盘面，没重置回合**。
新局必然红先，重建时强制 `side_to_move = "w"`。

**教训**
「重建盘面」不只是换棋盘数据，**回合、基准帧、遮蔽位、纠错计数全都要一起重置**。
少重置一样，表现都是「看起来卡住了」。

---

### 10. `MaterialGuard` 的计数永远凑不满

**现象**
子力跳变被拒 3 次后本该强制校准，实际却一直拒绝。

**根因**
计数 key 用的是差异**文案**（`"车多出 2 个"`）。识别每帧抖出来的文案不一样
（下一帧变成 `"车多出 2 个、马多出 1 个"`），key 一变计数就归零。

**修法**
改成纯计数，不比对文案。

---

### 11. 中途接管时死等对方走子

**现象**
程序在残局中途启动，明明轮到自己，却一直「等待对方走子」。

**根因**
启动时 `side_to_move` 硬编码 `"w"`。

**修法**
1. `turn_detect` 接入主循环：抓两帧比较上下两个头像计时器区域，哪边在跳就是哪边在走
   （`config.timer_regions` 里存着区域坐标，之前这个模块和配置都是**死代码**）；
2. 判不出时兜底：**只有与开局 90/90 完全一致才敢断定红方还没动过**，其余一律按
   「轮到我方」。门槛 85 太宽——红方走完第一步就差 2 格（88/90），会被误判成开局。

## 三、主循环：给出错误的建议

### 12. FEN 非法时静默跳过算棋

**现象**
用户视角：「走完这一步就不给方案了」，完全没有提示。

**根因**
盘面读出自相矛盾的组合（2 个将 / 3 个车），`fen_is_sane` 判定失败 → 打印一行日志后
跳过算棋。日志不显眼，界面上就是「不吭声」。

**修法**
`main.TrustGuard`：盘面不自洽 / 追踪失联 / FEN 非法 / 启动盘面可疑，任一发生就
**冻结出建议 2 帧**，并在界面上明确显示「暂不给出建议：<原因>」。

---

### 13. 在错误的盘面上算出「绝杀」，把用户走输

**现象**
第 3 局红方输了。复盘发现关键一手 `马六进四` 是程序建议的——它把挡住黑车的马挪开，
让黑车顺着空出来的直线吃掉了红车。

**根因链**
1. 该局日志里有 3 次 `FEN 异常，跳过算棋`、1 次「多帧最低票数 2」的重同步；
2. 重同步重建出的盘面**红方少一辆车**（`(2,1)` 那辆被判成空）；
3. **少子在象棋规则里完全合法**（被吃也算），`board_problems` 只查上限不查下限，
   所以全程零报警；
4. 引擎拿着「单车 vs 双车」的假盘面算，自然看不到双车下底杀，给出 `+6.63` 的
   炮退一步——而真实局面双车下底已经是绝杀。

**修法（两道）**
1. **出建议前独立复核**：重新识别整盘 → 与追踪盘面逐格比对 → 有任何差异先冻结，
   以重识别为准修正盘面；
2. **子力跳变校验** `board.material_jump()`：一步最多吃一个子，任何一方棋子只能
   「不变或 -1」。多出棋子、或一次少 2 个以上，都判不可信。

**教训**
这是整个项目最重要的一条：**错误建议比没有建议可怕得多**。用户会照着走，真丢子。
所以宁可冻结、宁可让用户等，也不要在一个自己都不确定的盘面上开口。

---

### 14. 提示卡刷屏

**现象**
残局阶段「暂不给出建议」的提示卡出现频率极高，看起来像程序坏了。

**根因**
重同步原本是**无条件冻结**的——但重同步成功后盘面已经是刚识别出来的干净状态，
没有理由再冻。加上「只多不少改为重组同步」后重同步频率上升，提示卡就刷屏了。

**修法**
只有重同步**被拒或失败**才冻结；冷却从 3 帧降到 2 帧。

---

### 15. 删文件导致预览面板显示「暂无数据」

**现象**
用户截图问「为什么这里显示暂无数据」。

**根因**
冻结时为了让过期箭头别误导用户，代码写了 `os.remove("bestmove.png")`。
而用户正开着预览面板看这个文件，一删就变成「暂无数据 / 当前文件已被删除」。

**修法**
`display.draw_void()`：覆盖成一张**作废图**（整体压暗 + 居中深色圆角卡「暂不给出建议 /
画面稳定后自动恢复」），文件始终存在。最早那版是贯穿全屏的大红叉 + `WAIT`，太糙，也改掉了。

**教训**
**不要用「删文件」表达状态**。文件消失对用户来说是「程序挂了」，而不是「这帧没有建议」。

---

### 16. 「暂停后卡死」——FEN 被提前消费

**现象**
冻结后本该 2 帧自动恢复，结果一直是「暂不给出建议」。

**根因**
`last_fen = fen` 写在 guard 判断**之前**。冻结时 FEN 被标记成「已算过」，
冷却结束后 `fen == last_fen`，永远不再重算。

**修法**
冻结路径**不更新** `last_fen`，等冷却结束按同一局面补算。

## 四、工程：配置与环境

### 17. `screen_size` 与 `capture_scale` 是相乘关系

**现象**
抓回来的图变成 154×338，识别全崩、`bestmove.png` 也变小了。

**根因**
为了修正四角，把 `screen_size` 从 `[1256, 2760]` 改成了 `[440, 966]`，
但 `capture_size()` 算的是 `screen_size × capture_scale = 440×0.35 = 154`，二次缩放。

**修法**
`screen_size` 是**标定截图尺寸**，`board_corners` 必须与它**同尺度**；抓图尺寸由
`capture_scale` 决定（1256×2760 × 0.35 ≈ 440×966）。

**教训**
改 `board_corners` 前先确认它属于哪个坐标系。

---

### 18. editable 安装写死路径，改名/迁盘就 import 失败

**现象**
目录改名后 `python -m xiangqi.main` 报 `ModuleNotFoundError: No module named 'xiangqi'`。

**根因**
项目做过 `pip install -e .`，`site-packages/__editable__.xiangqi_vision_assistant-0.1.0.pth`
里写死了旧路径。

**修法**
在新目录执行 `pip install -e . --no-deps --no-build-isolation`。
（已踩两次：改名一次、迁盘一次。）

---

### 19. 界面像「卡住」

**现象**
用户反复说卡住了，但后端一直在跑。

**根因（两个）**
1. 状态里的 `frames` 是空操作（`state["frames"] = state.get("frames", 0)`），永远是 0，
   没法区分「后端停了」和「只是没有新数据」；
2. 浏览器对后台标签页会节流定时器（可能降到一分钟一次），预览面板切到后台再回来，
   界面就是旧的。

**修法**
每帧推一次真实帧号和 `updated_at`，界面显示「N 秒前」，超过 15 秒标红「后端无响应」；
`visibilitychange` / `focus` 时立刻补一次刷新。

---

### 20. 前端改了却看不到

**根因**
浏览器缓存了 HTML 与静态资源。

**修法**
页面与静态资源全部加 `Cache-Control: no-store`，静态文件用自定义 `StaticFiles` 子类
统一加头。另外注意：`start_web.bat` 里的 python **必须带 `-u`**，否则 `main()` 的
`print` 被缓冲，日志里看不到任何输出，排查时会以为程序没跑。

---

## 五、测试

### 21. 阈值卡住测试

**现象**
给精修加 `max_shift_frac=0.45` 后，`test_refine_rectify_recovers_from_oversized_corners` 失败。

**根因**
那个测试构造的是「四角比交叉点网格外扩 70px」，在合成图尺度上正好是 **0.5 格**——
正当场景被新阈值误拒。

**教训**
加参数限制时，先看现有测试覆盖的**边界场景**，别凭直觉取值。最终定 0.7：
半格修正照做，整格级漂移才拒绝。

## 附录：判断「该不该信这个盘面」的清单

出建议前，程序会依次确认：

- [ ] 90 格里每颗棋子都落在规则允许的位置（士/象/帅）
- [ ] 每类棋子数量不超过上限，且超量时优先改判而非删除
- [ ] 与上一帧相比，子力变化不超过「被吃一个」
- [ ] 重新识别的盘面与追踪盘面逐格一致
- [ ] FEN 能被引擎接受（将帅不照面、不在被将死状态下轮到对方）

任何一条不过，就冻结，并告诉用户为什么。
